## 代码质量分析技能

### 核心能力

#### 1. 多语言代码质量检测
- **Java**: 圈复杂度、耦合度、设计模式应用
- **JavaScript/TypeScript**: ESLint规则、React最佳实践、Vue规范
- **Python**: PEP8规范、代码异味、性能瓶颈
- **Go**: Go语言规范、并发安全、性能优化
- **C#**: .NET规范、架构模式、性能优化

#### 2. 代码异味识别
- **重复代码**: DRY原则违反检测
- **过长方法**: 函数长度和复杂度分析
- **过大类**: 类大小和职责分析
- **深层嵌套**: 条件嵌套深度检测
- **复杂条件**: 布尔表达式复杂性分析

#### 3. 性能问题检测
- **算法复杂度**: 时间和空间复杂度分析
- **内存泄漏**: 资源管理和内存使用分析
- **数据库性能**: 查询优化和索引使用
- **网络性能**: API调用和异步处理优化
- **并发性能**: 线程安全和锁竞争分析

### 分析方法

#### 静态代码分析
```bash
# Java代码质量分析
mvn sonar:sonar
pmd-check -d src/main/java
checkstyle -c checkstyle.xml src/main/java

# JavaScript代码质量分析
npm run lint
eslint src/ --ext .js,.jsx,.ts,.tsx
prettier --check src/

# Python代码质量分析
flake8 src/
pylint src/
bandit -r src/

# Go代码质量分析
go vet ./...
golangci-lint run
gocyclo -over 15 .
```

#### 动态性能分析
```bash
# Java性能分析
jstack <pid> > thread_dump.txt
jmap -histo <pid> > heap_dump.txt
jstat -gc <pid> 1000

# Node.js性能分析
node --inspect app.js
npm run profile

# Python性能分析
python -m cProfile -o profile_output.txt app.py
line_profiler app.py

# Go性能分析
go test -cpuprofile cpu.out ./...
go test -memprofile mem.out ./...
```

### 质量指标评估

#### 代码质量评分
```markdown
## 代码质量评分体系

### 优秀 (90-100分)
- **代码结构**: 清晰、模块化、职责单一
- **设计模式**: 适当应用，提高可维护性
- **性能**: 优秀，无性能瓶颈
- **可读性**: 高，易于理解
- **测试覆盖率**: >90%

### 良好 (80-89分)
- **代码结构**: 结构清晰，少量冗余
- **设计模式**: 基本应用，偶有不规范
- **性能**: 良好，个别需要优化
- **可读性**: 较高，基本易懂
- **测试覆盖率**: 70-90%

### 一般 (60-79分)
- **代码结构**: 结构基本清晰，有重复代码
- **设计模式**: 应用不足，存在代码异味
- **性能**: 一般，存在性能问题
- **可读性**: 一般，部分代码难理解
- **测试覆盖率**: 50-70%

### 需要改进 (<60分)
- **代码结构**: 混乱，严重重复
- **设计模式**: 基本未应用，存在严重问题
- **性能**: 差，存在严重瓶颈
- **可读性**: 差，难以维护
- **测试覆盖率**: <50%
```

#### 复杂度指标
```markdown
## 复杂度指标标准

### 圈复杂度
- **简单 (<10)**: 易于理解和测试
- **中等 (10-20)**: 适中，可能需要重构
- **复杂 (>20)**: 难以测试和维护，需要重构

### 方法长度
- **理想 (<20行)**: 单一职责，易于理解
- **可接受 (20-50行)**: 偶尔有长方法
- **需要重构 (>50行)**: 应拆分为多个方法

### 类大小
- **理想 (<200行)**: 聚焦单一职责
- **可接受 (200-500行)**: 偶有冗余
- **需要重构 (>500行)**: 应拆分为多个类

### 参数数量
- **理想 (<3个)**: 简单清晰
- **可接受 (3-5个)**: 偶有多参数
- **需要重构 (>5个)**: 应使用对象或建造者模式
```

### 质量改进建议

#### 代码重构建议
```markdown
## 重构优先级和策略

### 高优先级重构
1. **消除代码重复**
   - 提取公共方法
   - 创建共享组件
   - 使用模板模式

2. **降低圈复杂度**
   - 提取条件判断
   - 使用策略模式
   - 简化嵌套结构

3. **减少方法长度**
   - 提取小方法
   - 应用单一职责
   - 提高可测试性

### 中优先级重构
1. **改善类设计**
   - 应用SOLID原则
   - 减少类间耦合
   - 增强内聚性

2. **优化性能**
   - 改进算法复杂度
   - 添加缓存策略
   - 优化数据库查询

3. **提高可读性**
   - 改进命名规范
   - 增加必要注释
   - 统一代码风格
```

### 最佳实践

#### 编码规范
```markdown
## 编码最佳实践

### 命名规范
- **类名**: 大驼峰命名，体现职责
- **方法名**: 动词开头，表达行为
- **变量名**: 小驼峰命名，表达用途
- **常量名**: 全大写下划线分隔

### 注释规范
- **类注释**: 说明类的主要职责
- **方法注释**: 说明参数和返回值
- **复杂逻辑**: 说明实现逻辑
- **避免过度**: 避免注释显而易见的代码

### 异常处理
- **特定异常**: 捕获具体异常类型
- **异常链**: 保留原始异常信息
- **资源管理**: 使用try-with-resources
- **日志记录**: 记录异常上下文
```
